# Design: 总控式并行开发

## Context

项目已有 OpenSpec 生命周期和审慎建议门禁，但尚未规定多个 Codex 窗口同时工作的所有权、写入隔离、同步方式与阻塞终止条件。当前保存项目根位于 Git 仓库父目录，任务窗口不能自动获得仓库 worktree；在该条件修复前，并发写入尤其容易互相覆盖。

## Decisions

### 1. 单总控、多执行窗口

一个窗口担任总控，负责读取完整 OpenSpec、维护依赖图、分配边界清晰的任务、监测关键路径、批准集成顺序、执行最终验证并同步任务状态。执行窗口只处理已分配的 OpenSpec 任务或有界前置研究，不自行扩大范围、创建竞争性设计或宣称跨任务完成。

### 2. 写入隔离优先，无法隔离时单写者

写入型任务优先在从同一已验证基线创建的独立 Git worktree 中执行，并以小提交交回总控。若应用保存项目未指向实际 Git 根、工作区存在未共享变更或无法安全建立 worktree，则并行窗口只进行只读研究；共享工作区在任一时刻只有总控指定的一个写入者。大数据、私有影像与 `artifacts/` 不复制到工作树，也不作为窗口间同步媒介。

### 3. OpenSpec 作为同步协议

任务分配必须引用任务编号、输入、允许修改的路径、验收命令、禁止事项和阻塞升级条件。执行窗口返回证据和提交，不直接改变其他任务状态；总控在集成并复验后统一更新 OpenSpec 复选框。研究结论在总控确认并更新 OpenSpec 之前不是产品决策。

### 4. 有限阻塞处理

阻塞处理按“采集首个相关错误 → 检查已批准且风险相称的推荐依赖或替代路径 → 进行一次有新增证据的修复 → 重新验证 → 升级”推进。同一命令或同一假设失败后，不得在没有环境、输入、配置或证据变化时反复执行；同一阻塞最多采用两个相互独立的安全修复方向。仍失败，或一开始就涉及产品架构、系统驱动/重启、账号与付费、许可证义务、数据外传或不可逆操作时，停止该分支并交由总控；总控无法在现有授权内解决时再交由用户决定。

### 5. 推荐依赖的安装边界

项目作用域、来源可信、版本固定、许可证已识别且可回退的构建/测试依赖，可以在已授权任务内由执行窗口安装并记录版本与验证。系统级运行时、驱动、虚拟化、全局环境切换、需要重启的组件、会改变最终产品架构或引入再分发义务的组件，即使被推荐，也必须遵守审慎建议门禁并由总控取得必要授权。安装不能替代根因分析，也不能把开发期工具自动变成产品运行依赖。

### 6. 模型偏好属于执行配置

用户明确指定时，总控窗口使用当前指定模型，新增任务窗口使用用户指定且当前环境可用的模型。模型偏好不进入产品架构或验收结论；无论模型如何，所有窗口遵守相同 OpenSpec、数据保护与验证门禁。

## Risks / Trade-offs

- 只读研究窗口不能直接提交实现，但可在 worktree 条件未满足时避免工作区冲突。
- 总控统一集成增加一道复验成本，但能避免任务状态虚报和跨分支规格漂移。
- 限制重试可能较早暴露真实阻塞；这是有意行为，阻塞应以证据升级而不是消耗式循环掩盖。

## Rollback

删除本变更引入的 `AGENTS.md` 并行协作章节，并恢复归档前的 `development-governance` 主规格；不涉及产品数据迁移。
