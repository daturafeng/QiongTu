## Context

当前仓库只有本次 OpenSpec 工件，没有既有代码或技术栈。系统目标已明确为类似大疆智图的 Windows 本地摄影测量生产软件，需要处理体积大、耗时长、失败模式复杂的任务，并同时生产二维 GIS、点云、纹理网格、网格 3D Tiles、原始三维高斯和 Cesium 高斯 3D Tiles。精度高度依赖采集条件，高斯兼容格式仍在演进，因此架构必须保存输入、空三、训练、转换和兼容性证据，不能只保存最终文件。具体行为边界见 `proposal.md` 与本变更下的能力规格。

首版采用以下产品假设：面向单个操作者，在 Windows x64 工作站本地安装；输入兼容性仅覆盖能够确认由受支持的大疆无人机直接采集的可见光航拍影像及其配套定位文件；网格与二维分支可按引擎能力使用 CPU/GPU，高斯训练首个实现以 NVIDIA CUDA GPU 为目标。界面可以使用 Web 渲染技术，但以桌面应用交付，计算、数据库、对象文件和本地 HTTP 成果服务均在用户工作站运行，不依赖把原始影像上传到公共云。多用户服务器、云算力、其他无人机品牌与通用相机输入，以及其他 GPU 后端属于后续扩展。

项目所有者提供了一个仓库外的多角度 JPEG/MPO 航拍样例及定位辅助文件。详细文件清单、内容指纹、设备与采集统计只保存在 Git 忽略的本地清点工件中；公开 OpenSpec 与基准登记只记录逻辑别名、数据类型、适用角色和私有清单绑定。该样例用于证明导入层必须识别真实容器、主摄影帧和制造商元数据，但不能单独决定引擎选型。

## Goals / Non-Goals

**Goals:**

- 用统一领域模型串联原始影像、质检、处理执行、成果和质量报告。
- 将摄影测量引擎隔离在可替换适配层中，通过真实无人机样本基准测试选择首个引擎。
- 在 Windows 工作站上完成导入、参数配置、计算、成果检查、导出和 Cesium 兼容预览的闭环。
- 先以受支持的大疆无人机影像完成并验证端到端重建闭环，再根据产品反馈决定是否扩展输入品牌。
- 共享一次权威空三结果，并从中派生正射/DSM、点云、纹理网格和三维高斯，保持所有成果坐标一致。
- 同时交付网格 3D Tiles 与使用当前高斯 glTF/SPZ 扩展的 Cesium 高斯 3D Tiles，并保留可重新转换的源成果。
- 单机首版可用，同时保留将控制服务、存储和计算工作节点拆分扩展的边界。
- 对长任务提供持久状态、资源保护、诊断和安全恢复。
- 为二维/三维在线浏览生成优化派生物，并保留标准高精度导出物。

**Non-Goals:**

- 不从零实现特征提取、SfM、MVS、网格重建或正射校正算法。
- 不在首版建设多租户 SaaS、计费、组织权限、公共分享或跨区域集群。
- 不在首版支持 AMD/Intel GPU 高斯训练、移动设备端重建或无 GPU 的高斯训练降级路径。
- 不在首版支持其他品牌无人机、通用相机或无法通过元数据/配套文件确认大疆采集来源的影像；这些输入不做兼容性承诺，也不提前建设品牌适配器。
- 不在首版实现航线规划、飞控、实时回传处理、完整 GIS 编辑或行业 AI 识别。
- 不把高斯表示当作拓扑网格、碰撞模型或测绘量测表面。
- 不以算法输出代替专业测绘验收，也不对未知采集条件承诺固定绝对精度。

## Decisions

### 1. 采用 Electron 桌面壳、独立 .NET 控制进程与隔离 Worker

首版固定采用 Electron 作为 Windows x64 桌面壳，React、TypeScript 与 Vite 构建项目、导入、质检、任务、成果和设置界面，CesiumJS 在同一受控渲染技术栈中提供二维/三维成果查看。Electron 自带并固定 Chromium，使 WebGL、Cesium、点云、网格 3D Tiles 与仍在演进的高斯扩展可以在已知浏览器版本上回归验证；Electron 和 Chromium 升级必须经过兼容矩阵、安全更新与固定查看样本回归，不能跟随 `latest` 自动漂移。

Electron 基线不能只在安装最新显卡驱动的开发机上决定。进入桌面生命周期实现门禁前，项目使用不含穹图业务代码的最小程序并排验证当前稳定版和仍受官方支持的上一条 Electron 稳定线，覆盖 Windows 10/11、集成显卡或无 CUDA、代表性的较旧稳定驱动、当前推荐驱动、硬件加速开启/关闭，以及向日葵等企业现场常见远程控制软件所安装的虚拟显示适配器和远程会话。选择默认 Electron 版本时同时权衡安全支持期、Cesium/WebGL/高斯兼容性和真实工作站成功启动率；旧版本只能在仍受官方安全支持且矩阵证据更优时选用，不能为绕过单机故障长期固定已停止维护的版本。若检测到已知不兼容的虚拟显示或远程会话，应用应在安全可行时提供可诊断的兼容启动路径；不得静默关闭系统设备、降低 Renderer 安全隔离或把停用用户远程运维工具作为默认修复。

桌面壳可启动门槛与高斯 CUDA Worker 门槛分离：受支持的 Windows x64 工作站即使没有 NVIDIA GPU、CUDA 或推荐版 NVIDIA 驱动，也必须能够打开应用、管理项目、查看兼容成果并运行满足条件的 CPU/普通摄影测量分支；控制服务只把不满足兼容矩阵的高斯或特定 GPU Worker 标记为不可用并给出升级建议。不得把为诊断某台开发机而升级的驱动版本直接变成全部用户的最低要求。

安装入口采用最小自包含 `.NET 10` Windows 原生进程 `QiongTu.Launcher.exe`，但它不是第二套产品 UI，也不拥有项目、数据库、任务或 Worker。启动器使用无需管理员权限的只读系统接口采集 Windows 版本/架构、远程会话、显示适配器与虚拟/间接显示驱动、物理 GPU 和驱动版本等启动关键证据，然后只从安装清单确定的固定路径启动已签名的 Electron 桌面程序。它不得接受普通用户提供的任意可执行路径，不得自动停用设备、安装或回退驱动、关闭安全软件、降低 Electron Renderer 隔离，也不得因 Electron 失败终止控制服务或已接管 Worker。

每次启动时，启动器生成当前用户作用域的一次性命名管道与高熵 nonce，通过子进程环境交给 Electron Main。Electron 在同一连接上依次发送 `main.started`、`app.ready`、`control.connecting`、`browser-window.creating`、`renderer.loaded`、`ready-to-show` 或相应失败事件，每条 JSONL 消息都包含协议版本、nonce、Electron PID、单调递增序号和枚举阶段，不携带本地路径或控制凭据；只有受限 BrowserWindow 的 Renderer 已成功加载并达到可显示状态后才能发送最终就绪事件。启动器以最后一个通过校验的阶段、Electron 退出码和只读环境证据进行分类，对连接、单条消息长度、事件数量和总等待时间设置上限；就绪后继续以低资源方式监视本次 Electron 进程，正常退出时直接结束，启动失败、就绪超时或异常退出时使用原生 Windows 对话框展示分类诊断、有限次重试和打开本地报告选项。重试必须创建新管道和 nonce，禁止无界自动循环。

启动诊断报告使用版本化 JSON，只记录产品/协议版本、时间、Windows 构建与架构、会话类型、显示适配器分类和驱动版本、Electron 启动阶段/退出码、规则标识、严重级别与可操作建议。报告默认写入当前用户本地应用数据的诊断目录，不包含用户名、计算机名、原始影像/项目路径、成果令牌、管道名、nonce、任意命令行或完整环境变量；对外导出前由用户明确确认。完整 CPU、内存、磁盘、CUDA 与显存能力仍由控制服务的任务 2.6 探测，启动器只负责桌面壳能否可靠启动所需的最小证据。

Electron Main 只负责窗口、单实例、系统托盘、受控目录选择、应用生命周期和启动/连接本地控制进程，不承担影像扫描、数据库、任务状态或重计算。Renderer 必须启用 sandbox 与 context isolation、禁用 Node integration，通过最小化且版本化的 preload 契约访问允许的桌面能力；默认拒绝任意外部导航、新窗口、非白名单协议和未经校验的文件路径，并使用严格内容安全策略。任何原始影像、密钥、任意系统命令或直接数据库连接都不得暴露给 Renderer。

独立的自包含 `.NET 10` `QiongTu.Control.exe` 是项目、SQLite、对象文件、任务状态、成果血缘、资源探测、回环成果服务和 Worker 生命周期的权威控制面。Electron 与控制进程通过当前用户作用域的命名管道承载版本化请求、响应和事件；不得为内部控制接口开放局域网端口。控制进程启动的摄影测量、高斯、Tileset 和导出 Worker 均为独立进程，使用显式输入/输出清单、工作目录和结构化事件，使 Electron 重启不终止已接管任务，单个 Worker 失败也不带崩其他分支。

控制进程在当前用户的本地应用数据目录中原子维护最小运行时发现文件，只记录协议版本、控制进程标识和随机化管道名，不记录成果令牌、原始影像路径或用户可识别数据。Electron Main 先读取并校验发现文件、连接既有控制进程，只有在进程或管道均不可用时才启动新的控制进程，并以有界退避重连；Electron 退出只关闭自己的管道连接，不向仍管理 Worker 的控制进程发送终止信号。命名管道采用长度受限的逐行 JSON 消息和当前用户访问限制，协议错误返回结构化失败，不允许透传任意命令行。

控制进程以 SQLite 运行时账本持久化 Worker 标识、注册类型、进程标识、状态和时间戳，并在启动时核对遗留进程；项目、数据集和成果等业务表及迁移仍由任务 2.3 定义。首版 Worker 启动请求只能引用控制进程内注册的 Worker 类型，实际参数由受信任清单构造，标准输出与错误输出写入应用管理的日志目录，取消使用先请求停止、超时后终止进程树的生命周期接口。对象文件根目录和可服务成果根目录同样只由控制进程登记，Renderer 与管道调用方均不能把任意系统路径注册为成果。

Cesium 与分块成果由控制进程绑定 `127.0.0.1` 随机端口的 HTTP 服务提供，使用进程会话令牌、成果白名单和目录越界防护，避免依赖 `file://` 并让本地预览与实际 Web 部署使用同一加载方式。命名管道负责控制通信，回环 HTTP 只提供查看器资源与成果字节，二者不得混为无鉴权通用 API。

回环成果服务每次控制进程启动生成新的高熵会话令牌；令牌只通过当前用户命名管道交给 Electron Main，不写入发现文件、日志或 Renderer 的通用状态对象。HTTP 只绑定 IPv4 回环随机端口，只允许读取控制进程已登记的成果根目录，规范化路径后拒绝越界、目录读取、非白名单成果和缺失/错误令牌。任务 2.2 先实现并验证该安全传输边界；Cesium 的具体成果授权与加载 UI 在任务 6.3 接入。

替代方案包括 Tauri、纯 WPF/WinUI、Qt 和 Electron 单体。Tauri 包体和空闲内存更小，但依赖系统 WebView2 版本，不利于固定 Cesium/WebGL/实验性高斯兼容环境；纯 WPF/WinUI 仍需嵌入 WebView2 承载 Cesium并形成双 UI 技术栈；Qt/C++ 增加开发和商业许可复杂度；把数据库、文件和重计算放入 Electron Main/Renderer 会扩大崩溃与安全边界。因此采用 Electron 作为界面壳、.NET 作为独立控制面、原生 Worker 作为计算面的混合架构。直接构建云端多租户平台仍不作为首版基线。

### 2. 摄影测量引擎通过命令级适配器集成

定义统一的引擎适配器协议：输入清单、坐标与控制信息、规范化处理配置、阶段事件、日志、检查点、原生输出清单和质量指标。引擎在受限工作目录的独立进程或容器中运行，控制服务不得依赖其私有目录结构。

首个引擎在实现前用代表性样本进行基准测试，评价成功率、正射与模型质量、CPU/GPU 支持、耗时、峰值内存/显存、输出完整性、许可和自动化接口。候选引擎可变化，但适配器契约和产品行为不随之变化。替代方案是直接把单一引擎命令散布在业务代码中；这会使升级、诊断和替换成本过高，因此拒绝。

任务 1.3 使用可复现、隔离的评测运行时执行固定版本的候选摄影测量引擎，并只生成 DOM、DSM、点云和纹理网格的比较证据。Docker Desktop 运行的 OpenDroneMap（ODM）可以作为一条评测路径，但 Docker、WSL 2、Hyper-V 和容器镜像均不得成为穹图最终独立 Windows 桌面软件的安装或运行依赖；必须同时保留可由产品安装包管理的原生 Windows 引擎适配路径。任何运行时、ODM 或原生组件的许可证、产品再分发资格和长期支持均不因本次实验自动获得批准，必须在任务 1.6 单独完成评审；实验报告必须记录宿主机、运行时、引擎版本、参数和输出校验值。没有成功运行的候选不得被选为产品引擎。

### 2A. 空三作为版本化权威中间成果，后续使用处理 DAG

影像特征、匹配、相机内参、相机位姿、稀疏点云、地理转换和质量指标构成一个不可变空三版本。DSM/正射、稠密点云、网格和高斯训练都是引用该版本的独立 DAG 分支；OBJ/FBX、网格 3D Tiles 和高斯 3D Tiles 又分别从对应正式成果派生。分支失败不使其他已校验分支回滚，修改相机位姿或地理配准则创建新的空三版本并使旧派生物失效。

替代方案是让网格引擎和高斯引擎各自重算相机位姿；这会造成重复计算、坐标不一致和无法可靠对比，因此拒绝。

### 3. 原始文件与派生成果进对象存储，关系数据库只保存权威元数据

影像、引擎中间文件、GeoTIFF、点云、网格、浏览切片和报告作为带校验值的对象保存；数据库保存项目、数据集版本、文件清单、任务状态、成果清单、空间范围、坐标参考和血缘关系。单机部署可使用兼容对象存储语义的本地实现，后续可替换为远程对象存储。

不把大二进制直接存入关系数据库，以避免备份、查询和迁移成本失控。临时工作目录与正式成果命名空间隔离，只有通过校验的成果才能原子发布。

本地对象存储在同一受控根目录内固定分为 `staging/<stage-id>/`、`quarantine/<quarantine-id>/` 和 `published/sha256/<前两位>/<完整哈希>` 三个命名空间。写入过程只以流式方式复制到随机暂存目录，同时计算 SHA-256 和字节数；文件数据刷盘并写入不包含源路径的版本化暂存清单后才形成可恢复的暂存对象。发布前必须重新核验暂存清单、长度和 SHA-256，并使用同卷不覆盖重命名把单个对象提升到内容寻址正式路径；目标已存在时只有在长度和内容哈希一致后才能去重，任何预期哈希不符、暂存被篡改或正式路径内容冲突都进入隔离并返回结构化失败，不能覆盖既有对象或产生表面成功。

控制进程重启时可以枚举并重新核验完整暂存清单，保留可恢复对象并把损坏或不完整对象转入隔离；不得自动发布缺少调用方业务元数据和校验结论的暂存对象。源文件始终以只读方式打开且不被移动、改名或删除。对象键只相对于 `published` 根目录保存，回环成果服务也只登记该正式根目录，因此即使客户端知道内部名称也不能读取暂存或隔离内容。任务 2.4 的原子性边界是单个不可变内容对象；跨多个文件、数据库成果状态和质量报告的一次性成果集合发布仍由任务 5.4 实现。崩溃发生在对象提升后、业务元数据登记前时可能留下安全但未引用的正式对象，后续引用保护与清理任务只能在宽限期和数据库核对后回收，不能为追求事务外观而删除可能有效的数据。

权威业务元数据使用独立的 SQLite 数据库 `state/qiongtu.db`；任务 2.2 的 `state/control-runtime.db` 只保存可核对、可重建的 Worker 运行账本。两者可以复用连接与 PRAGMA 策略，但不得共享 schema、迁移版本或故障恢复语义，避免运行时账本损坏或重建影响项目与成果血缘。业务数据库由控制进程独占迁移责任，每次连接启用外键、有限忙等待和 WAL，权威元数据采用 `synchronous=FULL`；启动迁移前后执行完整性快速检查，检测到损坏时保留原文件并拒绝写入，不自动覆盖或重建。

业务 schema 使用单调递增、按版本排序的嵌入式 SQL 迁移。`schema_migrations` 保存版本、不可变名称、SQL SHA-256 和应用时间，`PRAGMA user_version` 只作为最新版本镜像而非唯一事实来源。每个迁移及登记在同一事务中提交；重复初始化不得重复执行，失败不得留下半迁移状态。若已应用迁移的名称或校验值漂移、数据库包含当前程序未知的未来版本，控制进程必须在修改业务数据前停止并给出可诊断错误，不能静默降级。

首个业务 schema 以关系约束表达项目、数据集与不可变数据集版本、文件对象、影像与定位辅助文件、处理任务与多次执行、成果与成果文件、质量报告与发现项。稳定身份、生命周期状态、引用和查询字段使用有约束的列与外键；仅把版本化且需要扩展的参数快照、元数据来源证据、空间范围和质量指标保存为 JSON。文件对象只保存内容校验值、长度、媒体类型和受控对象键，不保存二进制或任意绝对路径；数据集版本封存后由数据库约束拒绝更新和删除。对象字节的写入、临时/正式命名空间及原子发布仍属于任务 2.4，项目 CRUD 与血缘 API 属于任务 2.5。

任务 2.5 的业务目录接口继续使用当前用户命名管道和既有 `qiongtu.control-api.v1` 信封，不开放新的局域网或回环业务 HTTP API，Renderer 也不得直接连接 SQLite。首批方法固定为 `project.create/list/get/confirm-crs`、`crs.recommend`、`dataset.create`、`dataset-version.create/list/get`、`result.list` 和 `result.lineage`；导入影像、提交处理、生成或发布成果分别仍属于 3.x、4.x 和 5.x。写方法把调用方在重试时保持不变的 `requestId` 作为幂等键，在同一 SQLite 事务中登记方法、规范化参数 SHA-256 和脱敏响应；相同键与相同请求返回原响应，相同键对应不同方法或参数则拒绝，防止管道断开重试产生重复项目或数据集版本。

列表接口使用稳定创建时间与实体标识组成的不透明键集游标，游标同时绑定方法和规范化筛选作用域，跨列表或跨筛选复用必须拒绝；默认页大小 20、允许范围 1—50，并返回精简摘要。详情和成果血缘按标识单独读取。请求标识和实体标识只接受 ASCII 字母、数字、点、下划线、连字符和冒号，所有名称、描述、CRS 定义、游标和筛选值也有显式长度边界。命名管道信封上限为 64 KiB，业务目录载荷最多使用 60 KiB，为版本、requestId 和结构化错误保留空间；超限写操作必须在登记幂等结果前回滚。成果血缘一次只返回目标成果、所属系列、项目、来源数据集版本、任务与执行、直接依赖、成果文件对象摘要和最终质量报告摘要；更深层血缘由客户端按直接依赖继续请求，避免无界递归、循环和超大响应。

坐标系推荐输入使用影像批次的 WGS84 经纬度范围，而不是未经依据的单点默认值。只有范围完全位于 UTM 适用纬度、没有跨赤道、反经线或多个 UTM 分区时，系统才返回 `recommended` 和相应 WGS84/UTM EPSG 快照；缺少范围或不满足条件返回 `not-recommended` 与单一稳定原因码。推荐不猜测垂直基准，使用 `unknown` 明确标记；项目只有在用户提交并确认一个完整、受限的 CRS 快照后才进入 `confirmed`，快照捕获时间由控制服务生成，后续更改默认 CRS 使用 `updated_at_utc` 乐观并发条件。同一 authority/code/垂直基准不能保存互相冲突的定义快照，v3 迁移发现历史歧义时保留 v2 数据并拒绝升级。已有成果继续引用生成时的 CRS 快照，不因项目默认值变化而重写。

### 3A. 复制前来源预检与复制后影像规范化分离

来源门禁必须先于原始内容复制。任务 3.2 使用 3.1 已建立的当前用户保护 locator、源身份快照和安全只读句柄，对候选影像的标准 EXIF 制造商/型号、DJI XMP 以及必要的同批次定位辅助文件头部执行有界只读预检。预检只生成脱敏的证据类别、冲突和失败原因，不保存绝对路径、完整相对路径、原始 EXIF/XMP、序列号、坐标、内容哈希或所有者样例派生统计，也不得 stage/publish CAS 对象、插入 `file_objects`/`images`/`image_frames` 或生成规范化帧。固定版本批次策略要求至少存在受支持且相互一致的 DJI 强证据，不得存在其他制造商或冲突证据；不能为每个候选建立一致覆盖、遇到不可读证据或达到读取上限时均保持 `unconfirmed`，不得凭文件名或扩展名放行。

来源预检使用独立的 `source_preflight_runs` 与 `source_preflight_items` 账本保存运行状态、固定 parser profile/version、批次结论、有界计数和脱敏原因。`image-import-preflight.start/get` 与 `image-import-preflight-item.list` 沿用命名管道、事务内 requestId 幂等、绑定作用域的 1—50 键集分页和 64 KiB 信封边界。批次结论不能由调用方提供，而是由 catalog 在结论事务内根据终态影像证据固定派生：不存在影像、读取失败或证据覆盖不足为 `unconfirmed`，明确其他制造商或证据冲突为 `out_of_scope`，只有全部影像在没有阻断证据时均支持 DJI 才为 `dji_supported`。批次结论、`dataset_versions.source_eligibility_state/source_evidence_json` 以及 3.1 会话/条目从 `awaiting_source_preflight` 到 `ready/discovered` 的数据库释放在一个 SQLite 事务中提交；只有 `dji_supported` 才执行释放，内存队列入队在事务提交后进行。预检中断保持数据集 `pending` 且不产生 CAS 对象；结论与数据库释放已提交但尚未入队时，3.1 控制进程恢复扫描负责幂等入队。`out_of_scope` 与 `unconfirmed` 都阻止复制和处理。中断运行只有在 3.1 对重新选择源完成同一影像账本的长度、修改时间和受保护身份复核后，才可在仍为 `interrupted` 时刷新源根与清单快照；运行中或终态运行不可重绑，sidecar 必须从新源重新发现并逐项复核身份。

任务 3.3 只在来源门禁通过、原始 `source_image` 已由 3.1 发布到正式 CAS 并完成业务登记后执行权威影像解析。系统依据内容而非扩展名识别 JPEG、带 MPF APP2 的 MPO 和 TIFF，记录全部帧/页、原始与有效尺寸、方向和结构证据，选择经结构与解码共同验证的高分辨率摄影主帧。可证明为独立 JPEG 字节范围的 MPO 主帧采用 byte-exact 提取；不能安全提取的输入只有在固定下游引擎接受的无损中间格式已验证时才转换，否则阻断并保留原始对象。任何路径都不得静默降采样、重复有损压缩或把低分辨率辅助帧送入重建，规范化对象必须内容寻址、版本化、幂等并记录到原始文件与帧的血缘。

影像元数据优先复用固定版本 `MetadataExtractor 2.9.3` 提取标准 EXIF/GPS/XMP 与 DJI maker note，再用本地字段映射记录 GPS、相机、云台/飞行姿态、RTK 标志和位置标准差的字段级来源；它不负责 MPO 帧语义或图像解码。JPEG marker、APP2 `MPF\0`/MP Index、嵌入 JPEG byte range 与 TIFF IFD/page inventory 由小型有界结构解析层负责，这只是容器证据与边界校验，不实现 JPEG/TIFF 解码器。解码、像素尺寸和可解码性验证复用固定版本 `Magick.NET-Q16-x64 14.16.0`；选择 Q16 而不是 Q8 是为了不把 16-bit TIFF 静默量化到 8-bit，Windows WIC 只作为可选交叉检查而不是 MPO 权威。上述 Apache-2.0 依赖的产品再分发仍须通过任务 1.6 最终许可门禁。

`Magick.NET` 原生库和外部影像解析不得加载到长生命周期的 `QiongTu.Control`。独立自包含 `QiongTu.ImageProbe.exe` 以固定安装路径和版本化 stdin/stdout 协议运行：来源预检 profile 只接收控制进程从已复核只读句柄代理的有界字节窗口，以及仅在 MRK 关联时使用、不得记录或回传的私有同组影像数量约束；CAS profile 只允许读取控制进程指定且重新验证位于正式对象命名空间的对象。子进程使用私有临时目录、超时、内存/磁盘/像素/帧数/metadata/输出/线程上限和 Windows 进程树约束；3.3a 不提供 URL、套接字或其他网络输入/依赖，禁用 ImageMagick 网络 coder、外部 delegate 和非 JPEG/MPO/TIFF coder。操作系统级 Worker 文件与网络沙箱属于任务 7.1，不能用 3.3a 的 coder/delegate policy 冒充已经完成。异常退出、原生崩溃、超时、资源上限或解析器分歧都转换为脱敏阻断原因，不能影响控制服务或静默选值。替代方案包括把 Magick.NET 直接载入控制进程、只用扩展名/WIC、依赖 ImageMagick 自动解释 MPF，或从零实现图像解码器；它们分别扩大故障域、缺少 MPO 保证、不能证明嵌入帧字节边界或重复成熟解码能力，因此拒绝。

`cas-image.v1` 不把最大 16 GiB 的正式对象复制到托管内存或 stdin。控制进程只接受内部 `PublishedObject` 身份，先按 SHA-256 与长度重新核验正式对象，再把正式对象根、规范对象键、预期 SHA-256 和长度放入有界 stdin JSON；这些值不得出现在命令行、stdout、stderr、业务 API 或普通日志。探测子进程独立规范化根与对象键、拒绝越界和任意 reparse point，以 `FileMode.Open`、`FileAccess.Read`、只共享读取的方式只打开一次对象，并在同一 `FileStream` 上复核长度/哈希、执行结构解析和向原生解码器提供可定位流；因此对象不能在检查期间被写入、删除或换包。结构解析只保留有界摘要并使用 checked/64-bit 算术，不把整文件或所有 metadata 物化；响应只含容器、帧/页范围与尺寸、位深/方向、解码状态、固定解析器/解码器身份、脱敏原因和全 false 隐私标志。JPEG/MPO 的 `ByteOffset/ByteLength` 表示可独立验证的 byte-exact JPEG 范围；经典 TIFF 页并非单一连续字节范围，首版以 IFD offset 和 `ByteLength=0` 表示页身份，strip/tile 范围只在结构层有界校验，不得把零长度误解释为可提取帧。

首版不采用 Windows inherited handle 作为 `Control` 到 `ImageProbe` 的正式对象 transport。该方案需要在重定向标准流之外自行封装 `CreateProcess`/`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`、复制句柄并维护显式继承白名单；直接依赖 .NET `ProcessStartInfo` 的全局可继承句柄会扩大无关句柄泄露风险，自定义原生启动层又会增加自包含发布、错误恢复和 Windows 兼容测试责任。当前 transport 的授权与字节身份仍由两层独立校验建立：`Control` 先通过对象仓库内部 API 校验 canonical 正式对象，子进程只接受规范根、由预期哈希确定的对象键和长度，逐级拒绝 reparse point，并在一次打开后用同一只读 `FileStream` 重新验证长度与 SHA-256，再把该流交给结构解析和原生解码；路径换包不会在预期哈希不一致时被接受。有界 stdin 是每次子进程私有的一次性控制通道，不属于 Renderer、业务 API、普通日志或结果协议。若后续威胁模型要求探测器完全不可见正式对象定位信息，可在保持 `cas-image.v1` 结果与上层业务契约不变的前提下，以经独立安全评审的原生句柄 broker 替换内部 transport。

首版 CAS 影像预算固定为：对象 1 byte—16 GiB、stdin header 64 KiB、stdout 64 KiB、stderr 8 KiB、最多 256 个 JPEG marker、256 个 MP entry 或 TIFF page、每个 IFD 最多 4,096 个 entry、单帧最多 1,000,000,000 像素、所有帧累计最多 2,000,000,000 像素、metadata/profile 累计 16 MiB、Magick 内存 512 MiB、memory-map 1 GiB、私有临时磁盘 4 GiB、线程 2、探测超时 60 秒、Windows Job 单进程内存 2 GiB。经典 TIFF 的 IFD/page、strip/tile 范围进入本阶段交叉验证；BigTIFF 会被结构识别但首版以 `bigtiff_not_supported` 稳定阻断，不能交给自动 coder 猜测。JPEG 必须有可闭合的 SOI/SOF/SOS/EOI 结构；MPO 的 MP Entry offset 以 MP Header TIFF 起点为基准，所有声明范围必须位于同一对象、互不重叠、指向完整可独立解码的 JPEG。CIPA MPF 允许两个 Individual Image 之间存在未约束字节，因此首版不强制相邻 MP Entry 无缝相接；帧间 gap 不作为影像或 metadata 解释、也不交给原生解码器，但最后一个声明 JPEG 后存在未声明尾随 payload 时稳定阻断。Magick 只在结构层已经确认容器后以显式 JPEG 或 TIFF format 读取；MPO 按经验证的独立 JPEG 范围逐帧解码，不依赖 Magick 自动解释 MPF。任何预算超限、结构/原生数量或尺寸分歧、原生异常、策略拒绝、进程失败和超时都返回稳定阻断原因；任务 3.3a 不提前写入 `images/image_frames` 或生成规范化对象，这些权威登记与幂等血缘属于 3.3b。

任务 3.3a 的完成边界是可由 `Control` 内部调用的隔离正式对象探测能力及其固定产品发布布局，不新增 Renderer/命名管道业务 API，也不建立影像检查、`images` 或 `image_frames` 账本。`project-dataset-management` 中“正式影像检查必须绑定可用 canonical `source_image`”约束由 3.3b 的权威清单事务落实：3.3b 只能把 3.3a 的已验证结果绑定到 `available` canonical 导入条目，损坏或不支持结论不得修改 3.1 终态。3.3a 的验收必须覆盖固定依赖与运行时身份、JPEG/MPO/TIFF 正向结构和原生交叉验证、畸形/越界/循环/未声明尾随 payload/资源炸弹、非 allowlist coder/delegate、子进程超时/崩溃/持续输出超限、恶意或畸形结果拒绝、`Control` 不加载 Magick.NET，以及自包含发布后 `image-probe/QiongTu.ImageProbe.exe` 的固定落位与可启动性；第三方再分发许可仍由任务 1.6 决定，不因 3.3a 技术验收通过而自动批准产品分发。

定位辅助文件在 3.2 只能以受控扩展和有界头部参与只读来源证据判断，不因此宣称文件已保存、解析、通过质量校验或参与处理。DJI 官方手册定义的 13 字段 MRK 图像日志布局只有在同一受保护源清单与私有相对目录中恰好存在一个 MRK、其照片序号从 1 连续且无重复、有效记录数完整覆盖同组影像，并且组内没有其他制造商、冲突或不可读影像时，才可作为 DJI 强证据；关联数量只在控制进程与隔离探测器之间使用，不进入 API、日志、公开工件或脱敏证据摘要。RINEX OBS/NAV 和 RTCM 3.x RTK 本身是跨厂商标准，只能作为配套文件存在/格式证据，不能单独证明 DJI 来源。不得用文件名、扩展名或任意文本中出现 `DJI` 字样代替结构与批次关联。任务 3.4 在来源门禁通过后才把支持的原文件发布为 `positioning_aux` 对象并建立批次关联；数据库分别记录原文件存在、解析成功、通过质量校验、参与某次处理四个状态，处理报告只把实际参与计算的数据列为精度依据。替代方案是把所有 `.jpeg` 当普通单帧 JPEG并忽略辅助文件；这可能造成引擎兼容问题和虚假的精度声明，因此拒绝。

任务 3.2c 把验收拆成两个互补边界：安全合成 EXIF/XMP/sidecar 批次使用真实隔离探测器和完整 coordinator 验证正向释放、阻断批次零 CAS/业务对象以及 API/数据库隐私；`owner-oblique-sample-v1` 仅在两个私有环境绑定同时存在时，通过其只读源和 Git 忽略清单执行本地 gated 验收。为避免私有样例一旦判定为 `dji_supported` 就复制整批内容，预检 coordinator 依赖一个内部“批准后入队”端口，生产组装固定绑定现有 `ImageImportCoordinator`，私有验收绑定 no-copy 实现并断言未产生 CAS、`file_objects`、`images` 或处理任务；安全合成 DJI 批次单独证明生产入队行为。私有清单验收只校验逻辑身份、只读政策和脱敏门禁，不输出或复制清单中的路径、内容指纹、数量、设备、坐标或派生统计，也不得把私有 inventory 作为公开测试输出。

### 3B. Windows 源目录导入采用受保护 locator、只读快照和可恢复内容发布

任务 3.1 只建立 Windows 本地目录与外接存储的原始影像候选导入会话，负责目录发现、只读复制、流式内容校验、重复检测、取消、源设备断开和控制进程重启恢复。复制前的 DJI EXIF/XMP 与必要 sidecar 来源预检、结论提交和门禁释放属于 3.2；正式 CAS 原始对象上的真实 JPEG/MPO/TIFF 容器识别、解码、多帧清单、主帧选择、规范化与完整影像元数据属于 3.3；MRK/NAV/OBS/RTK 正式保存与关联属于 3.4。3.1 不得以扩展名冒充容器结论，也不得把尚未执行的解码、制造商或定位字段写入 `images`。目录扫描只把固定版本策略支持的 `.jpg/.jpeg/.mpo/.tif/.tiff` 普通文件登记为影像候选；3.2 可以在同一受保护源根内按相同 reparse/身份/边界规则额外发现仅用于来源预检的 sidecar 候选，3.4 再决定是否正式保存。复制只能在数据集版本仍为草稿且来源预检状态为 `dji_supported` 时开始；未通过来源门禁的会话保持 `awaiting_source_preflight`，不得仅因底层复制器能读取文件而绕过首期范围。

导入器由控制进程执行，Renderer 只获得会话和条目的脱敏摘要。用户选择的绝对源根、完整相对路径和可恢复 locator 不得写入业务表、幂等响应、普通日志、质量报告或 Renderer 可见响应。每次安装生成随机导入密钥并使用 Windows CurrentUser 数据保护保存；业务库只保存该密钥 HMAC 后的源根键、源条目键、受限叶子展示名、长度/修改时间/文件身份快照、状态、stage receipt、内容对象绑定和脱敏失败码。需要自动恢复的绝对根与相对路径映射保存在当前用户保护的独立恢复清单中，文件名只使用会话标识；外接盘不可用、盘符变化或清单无法解密时会话进入 `awaiting_source`，用户重新选择源根后必须重新核对受保护清单和源身份才能继续。

扫描使用有界的手动递归，不跟随 junction、symlink、mount point 或其他 reparse point；源根、每层父目录和候选文件都要检查 reparse 属性，并阻断源根与 runtime/state/objects/logs 等控制数据目录互相包含。首版配置最多扫描 1,000,000 个文件系统条目、登记 100,000 个候选、递归 64 层、单文件 16 GiB；达到边界时以结构化状态停止，不能静默截断后宣称完整。候选按规范化相对路径稳定排序，但明文相对路径只存在于受保护清单。源文件以 `FileMode.Open`、`FileAccess.Read`、不允许写入/删除共享的只读句柄打开；打开后及复制结束前后复核文件身份、长度和修改时间。枚举后或复制期间发生替换、截断或变化时放弃/隔离暂存对象并标记可重试源变化，不能把变化后的字节静默归入原快照。锁定、设备断开与暂时不可用是可重试来源状态；3.1 的损坏仅指无法只读打开、复制内容校验失败、stage 被篡改或对象发布完整性失败，不把影像解码失败提前算作 3.1 损坏。

对象字节继续统一写入 `ContentAddressedObjectStore`。3.2 在事务中提交 `dji_supported` 后，以确定性的内部释放键调用现有 coordinator；控制进程恢复也会扫描“已放行但仍等待预检”的会话并幂等释放，避免结论提交与入队之间的崩溃窗口。之后导入条目先持久登记，再流式 stage；stage manifest 刷盘后保存 receipt；正式提升前把条目标为 `publishing` 并保存预期 SHA-256/长度/正式相对键；对象提升成功后在单个 SQLite 事务中插入或复用 `file_objects`，并把条目标为 `available` 或 `duplicate`。`file_objects` 的 SHA-256 与长度唯一约束是跨会话去重权威，同一会话后续相同内容指向首个 canonical 条目且不重复保存字节。控制进程启动时只恢复能与账本 receipt 匹配的完整 stage；缺少业务元数据的孤儿 stage 不自动发布。若崩溃发生在正式对象提升后、业务提交前，恢复流程按预期哈希和长度核验正式对象并补登记，不能重复复制或为追求事务外观删除可能有效的正式对象。start/resume/cancel 写方法沿用事务内 requestId 幂等，get/list 与条目列表沿用绑定作用域的 1—50 键集分页和 64 KiB 信封边界。

本阶段优先组合既有成熟能力：源 locator 密钥保护使用 Windows CurrentUser DPAPI，源读取使用 .NET/Windows 安全文件句柄与流式 I/O，权威账本复用既有 SQLite 迁移与幂等机制，内容字节复用任务 2.4 的 `ContentAddressedObjectStore`，不另造密码算法、数据库、对象仓库或通用复制框架。本地新增代码只负责这些能力之间的有界枚举、HMAC 不透明标识、状态转换、命名管道契约和崩溃窗口补偿。已评估的替代方案中，`FileSystemWatcher` 只提供易丢失的变化通知而不形成一致只读快照，`File.Copy`/Windows CopyFile 不能同时提供同句柄前后身份复核、流式内容寻址和 stage receipt，通用云对象存储或第三方同步库会引入网络、再分发和路径暴露边界且仍不能替代本地业务事务，因此不适用于首版离线导入；后续若引入成熟导入/取证组件，仍必须通过相同契约与隐私验收后替换内部实现。

### 4. 使用持久任务状态机和资源感知的工作队列

控制面是任务状态的唯一权威来源，工作进程以带租约的方式领取执行。每个阶段持续写入心跳、结构化事件和日志引用；失去租约的执行不会继续发布成果。取消采用先请求优雅停止、超时后强制终止的两阶段策略。重试创建新的执行记录，只有校验通过且版本兼容的检查点可复用。

首版默认限制同一工作站的高资源任务并发数，并在启动前评估磁盘、内存和 GPU 条件。替代方案是直接在 API 请求内启动进程；这无法可靠处理重启、取消和并发资源竞争，因此拒绝。

任务 2.6 先建立处理能力事实与 Worker 准入边界。控制服务通过 `capability.get` 返回版本化、脱敏的 CPU、物理内存、受控 runtime/object/log/worker 目录所在卷、NVIDIA 驱动 API、CUDA Driver API、GPU 和显存快照，并通过 `worker.admission.check` 返回某个已注册 Worker 的 `allowed`、`denied` 或 `unknown` 结论。探测状态明确区分 `present`、`missing` 与 `unknown`，准入原因再区分 `missing`、`unknown`、`incompatible` 和 `insufficient`；不得把“探测失败”伪装为“硬件不存在”，也不得把缺少 CUDA 解释为桌面应用不可启动。

CPU、内存和磁盘使用无需提权的 Windows/.NET 只读接口；报告只返回卷角色和容量，不返回盘符、绝对路径、用户名、机器名、项目路径或环境变量。NVIDIA/CUDA 厂商驱动调用必须隔离：控制服务只以 `Environment.ProcessPath` 指向的自身固定可执行文件启动内部 `--hardware-probe-child` 模式，设置 5 秒超时、禁用 shell、限制 stdout/stderr 大小并在超时后终止子进程树。子模式动态加载系统 `nvml.dll` 与 `nvcuda.dll`，读取驱动、CUDA Driver API、设备名称和显存；缺少 DLL、初始化失败和超时以结构化状态返回。产品不调用 PATH 中的任意程序，不依赖 `nvidia-smi`、`nvcc`、系统 CUDA Toolkit、Docker、WSL 或 Node.js；计算 Worker 应随安装包携带经许可审核的用户态运行库，并以兼容矩阵检查其所需 Driver API。

Worker 资源需求作为 `WorkerDefinition` 的固定、版本化配置保存，至少包含逻辑处理器、可用内存、工作卷可用空间、是否需要 NVIDIA、最低 CUDA Driver API、最低总显存和最低当前可用显存。控制调用方只能提交已注册 `workerType`，不能自行降低要求或提供可执行路径。`worker.start` 在创建进程与运行账本前执行同一准入检查；任一硬性需求为 `missing`、`incompatible` 或 `insufficient` 时返回 `worker_admission_denied`，关键事实为 `unknown` 时返回 `worker_admission_unknown`。真正的跨任务资源预留、动态采样和 GPU 独占队列仍属于任务 4.5/4.6，2.6 不以瞬时探测替代原子资源预留。

任务 2.7 以真实 SQLite 业务库、内容对象存储、命名管道和操作系统 Worker 进程为集成边界，而不是用单元替身重复证明单表或单类行为。验收矩阵固定覆盖四条链路：处理任务封存数据集版本后旧清单和旧成果仍不可变且新变更进入单调递增的新版本；正式内容对象登记到发布成果后，文件快照、依赖、最终质量报告和被引用数据集受到数据库与对象存储双重保护；成果血缘通过真实管道只返回权威直接关系和正式相对对象键，篡改尝试被拒绝后不会推测或污染结果；桌面客户端异常断开不终止控制进程接管的 Worker，控制进程重建监督器时只按固定可执行身份重新接管存活进程，并把不存在或身份不符的账本记录标记为 `lost`。这些测试只验证 2.x 已实现的持久化与生命周期边界，不在 2.7 内虚构尚未实现的 3.x 导入 API、4.x 任务状态机或 5.4 多对象成果集合事务。

### 5. 正式成果与浏览派生物分离

二维正式成果使用带完整坐标信息的 GeoTIFF；为浏览生成具有金字塔和范围读取能力的栅格表示。三维正式成果保留 LAS/LAZ/PLY 点云、带纹理 OBJ/FBX 网格和包含完整属性的原始高斯；为浏览分别生成分层网格 3D Tiles、点云浏览成果和 Cesium 高斯 3D Tiles。派生物记录来源成果版本，可以删除并重建，但不能反向覆盖正式成果。

这一设计增加存储占用，却显著降低浏览器首屏时间和内存压力，也保持与外部 GIS/三维工具的互操作性。

### 5A. 网格 3D Tiles 采用 3D Tiles 1.1 与 glTF/GLB 内容

网格转换器将纹理网格按空间与几何复杂度分块，生成包围体、几何误差、层级关系、纹理 LOD 和 `tileset.json`，优先采用 3D Tiles 1.1 直接 glTF/GLB 内容。旧式 B3DM 仅作为明确的兼容导出选项，不作为内部主格式。转换器保存源网格校验值、局部坐标系、地理变换和版本，发布前用验证器和固定 CesiumJS 测试页检查。

OBJ/FBX 使用局部工程坐标以避免大地坐标导致单精度损失，并随文件提供坐标参考、局部原点、轴向和单位说明；3D Tiles 根变换负责从局部坐标转换到 ECEF/地球场景。

### 5B. 三维高斯保留源成果并生成 Cesium 专用 Tileset

高斯训练器消费权威空三中的已注册影像、相机内参与位姿，在局部高精度坐标系中生成包含位置、旋转、尺度、不透明度和球谐颜色系数的源成果。训练器、清理器、裁剪器、LOD/分块器和 Cesium 编码器是独立阶段，均保存版本与参数。

Cesium 编码器把高斯块写入 glTF/GLB，使用 `KHR_gaussian_splatting` 表达属性，使用 `KHR_gaussian_splatting_compression_spz_2` 与 SPZ 压缩，并以 3D Tiles `tileset.json` 建立空间索引和 LOD。根变换显式完成本地坐标轴、局部原点与 ECEF 的转换。源高斯不绑定 Cesium 扩展版本，确保扩展升级时只需重新编码和切片。

不采用 DJI TerraGS 作为 Cesium 交付格式，因为它不是本产品的 Cesium 互操作契约；如未来需要，可另做导入适配器。

### 5C. Cesium 兼容性是发布门槛而非演示功能

项目固定一个最低兼容 CesiumJS 版本，并在发布时记录实际验证版本。自动化验收通过本地 HTTP 服务使用原生 `Cesium3DTileset.fromUrl` 分别加载网格和高斯 `tileset.json`，检查扩展声明、请求成功、包围体、地理位置、方向、尺度、LOD 切换、控制台错误和基础性能。不得通过修改 Cesium 源码或注入私有渲染插件让不合格成果“通过”。

由于高斯扩展仍处于快速演进阶段，CesiumJS 与高斯编码器必须分别固定版本；升级先对参考成果重切片和回归，再改变默认导出版本。

### 6. 质检结论分为阻断、警告和信息，精度使用证据等级表达

所有质检规则输出原始指标、阈值和解释。只有结构性无效输入作为阻断项；可能仍能产生结果的数据质量问题作为需确认警告。精度不使用单一营销数字，而根据定位来源、控制点、重投影误差、GSD 和验证点等证据标记“相对模型”“地理参考可视化级”或经配置验收的更高等级。

替代方案是自动修复或隐藏异常，以提高表面成功率；这会使用户无法判断结果是否适合量测，因而拒绝。

### 7. 先建立独立多来源的固定验收组合，再优化性能

验收组合不得依赖单一用户样例或从同一批影像切出的全部变体。至少登记五类合法可使用且来源相互独立的数据：小型规则正射航拍；包含倾斜视角的建筑/复杂场景；带独立控制点、检查点或参考成果的精度验证数据；具有训练/验证视角的三维高斯视觉质量数据；以及基于允许派生的素材或项目自生成素材构造的模糊、缺 GPS、损坏、重复、低重叠等故障数据。首版真实影像基准的“来源相互独立”是指不同采集批次或数据发布，而不是不同无人机品牌；每个进入首版引擎选型或发布门禁的真实影像数据集还必须保存可核验的大疆采集来源证据。每个数据集保存来源、许可与再分发边界、内容身份、预期注册率、空间范围、输出类型、质量区间和适用/不适用目标。外部素材许可或大疆采集来源不明确时只能登记为候选，不得下载、提交或作为首版发布门禁证据。

对于项目所有者提供且未授权公开再分发的样例，“内容身份”和详细空间/采集统计 SHALL 保存为私有本地清单，通过环境绑定供测试读取；公开仓库只记录清单状态，不包含可用于识别同一原始集合的指纹或聚合特征。公开领域或明确许可的外部发布可以记录 DOI、官方目录标识、许可链接和公开参考指标。

引擎候选必须在至少两个相互独立的真实航拍来源上产生可比较结果，并分别在精度数据、高斯视角数据和故障数据上完成适用专项验证；任何单一数据集的成功都不能决定引擎或参数。所有引擎升级与参数变更都运行相同组合的回归基准。

当前阶段先使用 `owner-oblique-sample-v1` 运行本地可行性预演，验证候选引擎对私有多角度 JPEG/MPO 和定位辅助文件的导入行为、DOM、DSM、点云和纹理网格输出，以及资源与失败证据。该预演只能使用私有本地清单绑定的只读输入，所有规范化副本、引擎工作目录、日志和派生成果保存在 Git 忽略的本地 `artifacts/` 下；公开记录不得包含样例的内容指纹、数量、设备或采集统计。预演结果明确标记为“单样例、不可用于引擎选型或泛化声明”。

Fall Creek 2016-11-09 与 Medina River 2019-08-14 保持为后续多来源基准候选，但当前不再物化或下载；已产生的本地部分下载只保留在 Git 忽略目录，可在用户重新授权且来源资格复核后续传。它们只有在能够核验为大疆无人机采集时才能进入首版正式基准，否则转为产品成功后的跨品牌兼容研究候选。完成正式引擎选型前，仍须在至少两个相互独立、且具有大疆来源证据的真实采集来源上以相同配置完成可比较结果；Medina River 2022-07-08 同样按此资格门禁决定是否进入任务 8.2。

首次容器候选固定为 `opendronemap/odm@sha256:8ebfd231a56192da08fdbe1e6950aeba9c8c963af2f48e60c532731bc326b2b0`（ODM 3.6.1，Linux/amd64）。首轮使用 CPU 路径以消除 GPU 透传、显存和 GPU 镜像差异：`--dsm --pc-las --pc-quality medium --orthophoto-resolution 5 --dem-resolution 5 --mesh-size 200000 --mesh-octree-depth 11 --max-concurrency 4 --no-gpu`。该配置生成 DOM、DSM、LAS 点云和纹理网格；GPU 路径须在固定同样本和参数后作为单独的后续对照实验，不能混入本次基线。

没有固定数据集就直接按单次演示效果调参，会导致质量不可复现，因此验收数据先于完整界面开发。

`owner-oblique-sample-v1` 是项目所有者提供的一个私有端到端逻辑样例，用于验证多角度 JPEG/MPO、定位辅助文件以及完整成果链。它适合暴露特定复杂场景失败模式，但不代表独立规则正射、精度控制、高斯新视角或跨设备泛化数据，不能单独承担引擎选型和发布验收。

## Risks / Trade-offs

- [普通 GPS、低重叠或反光/水面/植被导致成果漂移或破洞] → 在处理前质检、处理后报告中暴露证据，并用验收数据定义可接受区间。
- [大数据集耗尽磁盘、内存或显存] → 提交前估算、保留安全余量、限制并发、隔离临时目录，并提供生命周期清理策略。
- [第三方引擎版本或许可证限制产品分发] → 在基准阶段完成许可证审查，固定引擎版本与镜像摘要，通过适配器降低替换成本。
- [高斯训练对 NVIDIA 驱动、CUDA、显存和算子版本敏感] → 安装时执行环境探测，发布经验证的兼容矩阵，训练进程隔离并保留可诊断日志。
- [高斯 glTF/SPZ 扩展或 Cesium 实验性支持发生破坏性变化] → 固定版本、保存源高斯、转换器模块化，并对每次升级执行重新切片与 Cesium 回归测试。
- [单一超大高斯文件在 Cesium 中耗尽网络或显存] → 强制空间分块、LOD、SPZ 压缩、并发请求控制和显存预算，不把单文件 PLY 直接作为生产交付。
- [FBX/OBJ 大坐标导致精度丢失或轴向错误] → 使用局部工程坐标并附带 CRS/原点/轴向/单位说明，外部格式回读后执行范围与方向校验。
- [高斯视觉效果被误用于工程量测] → UI 和报告明确成果类型，量测绑定 DSM、点云或网格几何，不以高斯着色结果作为测量表面。
- [任务进度无法精确量化] → 优先显示真实阶段、活动与已完成计数；只有引擎提供可靠数据时才显示百分比。
- [浏览派生物与正式成果不一致] → 使用内容校验和、来源版本及幂等生成，任何来源变化都使旧派生物失效。
- [单机架构限制并发与可用性] → 首版明确并发边界；队列、对象存储和无状态 API 边界为后续拆分工作节点保留迁移路径。
- [坐标和垂直基准处理错误造成危险量测] → 强制保存 CRS/垂直参考来源，转换使用经过验证的坐标库，对未知垂直基准显式标记而不猜测。
- [扩展名为 JPEG 的 MPO 被误读为低分辨率帧或被重复有损转换] → 内容识别、显式主帧选择、像素尺寸校验和无降采样规范化，并保留原始文件。
- [过早兼容多品牌导致元数据、相机模型和辅助文件差异扩大首版测试矩阵] → 首期只接受可核验的大疆无人机采集输入，以独立大疆批次验证泛化；其他品牌在产品闭环成功后通过独立 OpenSpec 变更评估。
- [存在 RTK 辅助文件但并未实际用于处理却被误报为高精度成果] → 分离“存在、解析、校验、参与处理”状态，质量报告只引用真实执行证据。

## Migration Plan

这是全新项目，无存量数据迁移。交付按可回退阶段推进：先以大疆无人机影像完成 Windows 桌面骨架、数据模型、来源识别、导入质检和固定样本；再接入空三、DOM/DSM、点云与网格；随后开放 OBJ/FBX 和网格 3D Tiles；最后接入高斯训练、源高斯、Cesium 高斯 Tileset 与兼容性门槛。每个阶段的持久数据都带 schema、引擎、训练器、转换器和格式版本，升级失败时可回滚应用与默认导出版本，已发布的不可变成果仍可读取，源成果可重新转换。首版闭环与市场验证完成后，若确有需求，再创建新的 OpenSpec 变更扩展其他无人机品牌或通用相机输入。
