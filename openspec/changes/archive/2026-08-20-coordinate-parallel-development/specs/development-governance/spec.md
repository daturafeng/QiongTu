## ADDED Requirements

### Requirement: 并行开发必须由单一总控按 OpenSpec 任务协调
当多个 Codex 窗口同时参与项目时，项目 MUST 指定一个总控窗口维护任务依赖、写入所有权、集成顺序、验证与 OpenSpec 状态。每个执行窗口 MUST 只处理明确分配的任务编号、输入、允许路径和验收范围，不得自行扩大任务或建立与 OpenSpec 竞争的事实来源。

#### Scenario: 创建并行执行窗口
- **WHEN** 总控识别出不依赖同一未决决策且可独立验收的任务
- **THEN** 总控为窗口提供任务编号、边界、允许修改路径、验证命令和阻塞升级条件，并持续保留最终集成责任

#### Scenario: 并行任务返回结果
- **WHEN** 执行窗口完成实现或研究
- **THEN** 总控复核证据、在目标基线上重新验证并完成集成后，才更新对应 OpenSpec 状态或采用研究结论

### Requirement: 并发写入必须隔离或退化为单写者
写入型并行任务 SHOULD 使用独立 Git worktree 和可追溯提交。若无法从同一已验证基线安全创建 worktree，项目 MUST 保持共享工作区单写者，并将其他窗口限制为只读研究或等待，不得让多个窗口同时修改重叠文件。

#### Scenario: 保存项目未指向 Git 仓库根
- **WHEN** 任务窗口不能安全创建仓库 worktree
- **THEN** 总控只分配只读研究，或先修复项目/worktree 前置条件，再启动并发实现

#### Scenario: 两个任务需要修改同一规格或源文件
- **WHEN** 并行任务的允许路径发生重叠
- **THEN** 总控串行化这些任务或重新划分所有权，不允许最后写入者覆盖另一任务

### Requirement: 阻塞处理必须有限、证据驱动并适时升级
执行窗口 MUST 记录首个相关错误，并且 MUST NOT 在环境、输入、配置或证据未变化时重复相同失败操作。同一阻塞最多尝试两个相互独立且风险相称的安全修复方向；仍无法解决时 MUST 停止该分支并把证据交给总控。总控在现有授权和安全边界内仍无法解决时 SHALL 请求用户决定。

#### Scenario: 推荐依赖可以安全解决阻塞
- **WHEN** 阻塞可由来源可信、版本固定、许可证已识别、项目作用域且可回退的依赖解决
- **THEN** 执行窗口可在已授权任务内安装、记录版本并重新验证一次

#### Scenario: 推荐依赖改变重大边界
- **WHEN** 安装需要系统驱动、重启、全局环境切换、账号或付费，或改变产品架构、数据外部影响和再分发义务
- **THEN** 执行窗口停止安装并将选项与证据交给总控，由总控按审慎建议门禁取得用户选择

#### Scenario: 两种安全修复均失败
- **WHEN** 同一阻塞的两个独立修复方向均留下失败证据
- **THEN** 执行窗口不继续循环尝试，报告阻塞、影响和可由用户或外部状态解除的条件

### Requirement: 并行窗口必须遵守统一的数据与依赖边界
执行窗口 MUST NOT 因并行化而复制、提交或外传私有原始影像、大型成果、密钥或机器专属信息。开发期依赖和容器 MUST NOT 因并行任务使用而自动成为最终产品运行依赖。

#### Scenario: 研究任务不需要私有样例
- **WHEN** 候选组件、技术栈或许可证可通过代码库和官方资料评审
- **THEN** 执行窗口不得访问私有影像，且不得下载大型数据集

#### Scenario: 并行任务使用开发期容器
- **WHEN** 容器仅用于隔离基准或验证
- **THEN** 结论明确标记容器为开发期可选路径，并继续保留产品原生分发门禁
