## Context

项目已有 OpenSpec 目录和两个产品相关活动变更，但根目录没有项目级 `AGENTS.md`，`openspec/config.yaml` 仍是空白模板，目录也尚未初始化 Git。用户指定的参考任务给出了从目标验证、MVP、规格、设计、实现、测试、试运行、上线到运营迭代的完整生命周期。需要把该流程转化为能够被新会话自动发现、由 OpenSpec 约束并可以检查的本地治理机制。

## Goals / Non-Goals

**Goals:**

- 后续会话进入本项目时自动获得同一套强制启动检查、阶段门禁和完成标准。
- 让详细流程存在 OpenSpec 主规格中，避免 AGENTS、临时计划和说明文档形成多个事实来源。
- 用 OpenSpec 配置约束 proposal、specs、design、tasks、apply 和 archive 的质量。
- 既覆盖当前的单机无人机处理软件开发，也能约束后续测试、试运行、发布和运营变更。
- 在没有 Git 和业务代码的早期阶段立即生效，并为后续工程化保留明确门禁。

**Non-Goals:**

- 不在本变更中初始化 Git、选择业务技术栈、实现产品功能或搭建 CI/CD。
- 不创建 OpenSpec 之外的第二套需求、设计或实施计划模板。
- 不把所有任务都强制成相同测试矩阵；验证深度按风险和影响范围调整。
- 不把一次会话的聊天记录作为后续工作的事实来源。

## Decisions

### 1. 使用三层持久化，但只保留一个详细事实来源

根目录 `AGENTS.md` 作为自动加载的执行入口，只保存必须遵循的行为、启动检查、门禁和指向 OpenSpec 主规格的引用。`openspec/config.yaml` 保存 CLI 可消费的项目上下文和工件/操作规则。归档后的 `openspec/specs/development-governance/spec.md` 保存完整、可验证的生命周期契约。

不另建独立的“开发计划.md”或“需求模板”体系，因为它们容易与 OpenSpec 冲突。AGENTS 与 config 只能提炼和执行主规格，不得重新定义相反规则。

### 2. 会话启动使用固定检查顺序

软件工作开始时依次检查：根目录指令、OpenSpec CLI 与配置、活动变更列表、适用变更工件、任务状态、仓库/环境状态、与请求相关的现有代码和验证命令。先判断请求属于探索、更新规格、实现、诊断、验证、发布还是运营，再选择对应 OpenSpec 工作流。

这样可以避免新会话忽略既有决策、重复创建变更或在缺少规格时直接写代码。

### 3. 生命周期使用可审计门禁而不是时间阶段

流程表示为：

`探索与目标 → MVP/提案 → 可验收规格 → 技术设计 → 可执行任务 → 实现 → 验证 → 发布准备 → 试运行 → 正式发布 → 运营反馈`。

阶段是否通过由工件和证据决定，而不是由时间或口头声明决定。小型变更可以压缩阶段，但不能跳过适用的需求、验证和回滚责任。

### 4. Ready、Done、Release 三类门禁各自负责不同风险

- Definition of Ready 阻止含糊任务进入编码。
- Definition of Done 阻止只有正常路径或缺少验证的功能被标记完成。
- Release Gate 阻止尚不可安装、恢复或回滚的版本进入真实使用。

三个门禁写入主规格，AGENTS 提醒执行，OpenSpec tasks 记录逐项进度。后续 CI 可自动化其中的机械检查，但不是本次变更的前置条件。

### 5. OpenSpec 配置约束工件最小质量

`openspec/config.yaml` 将记录项目领域与交付形态，并添加以下规则：proposal 必须含目标用户、价值、成功指标、MVP 和非目标；specs 必须包含异常、恢复、兼容与数据保护场景；design 必须包含备选方案、资源/性能、安全、部署、回滚和验证策略；tasks 必须可在单次会话完成、可验证并按依赖排序。

apply 操作要求先检查任务 Ready 状态，按任务实现并在验证后更新复选框；archive 操作要求任务完成、严格校验通过、验证与已知风险有记录，并同步主规格。

### 6. Git 门禁延迟到仓库初始化后生效

当前不存在 Git 仓库，治理规则必须如实记录限制，不执行虚假的分支、提交或 CI 检查。用户初始化 Git 后，后续会话自动把 OpenSpec、源代码、配置和迁移纳入版本控制，并执行小提交、密钥排除和合并前验证规则。

## Risks / Trade-offs

- [AGENTS 过长导致后续会话忽略重点] → AGENTS 只保留可执行规则和启动清单，详细解释放在 OpenSpec 主规格。
- [AGENTS 与 OpenSpec 主规格逐渐冲突] → AGENTS 明确 OpenSpec 主规格优先，流程变化必须通过新的 OpenSpec 变更同步两者。
- [严格门禁拖慢早期探索] → 探索阶段允许只读研究和假设记录，但任何正式设计或实现仍需完整工件。
- [没有 Git 时治理证据可能丢失] → 当前先落地本地 OpenSpec 与 AGENTS，并明确风险；需要提交、分支或回滚历史时再请求初始化 Git。
- [所有任务套用同样测试导致成本过高] → 采用风险分级，保留最小验证要求并对坐标、GPU、大文件、安装和数据安全增加专项验证。

## Migration Plan

先创建并严格校验本治理变更；随后新增根目录 `AGENTS.md`、更新 `openspec/config.yaml`，按任务验证内容和自动发现路径。实现完成后同步任务状态，将变更归档为 `openspec/specs/development-governance/spec.md`。回滚时可恢复旧 config 并移除项目级 AGENTS，但应保留已归档治理规格和变更历史，以便了解规则曾经为何存在。
