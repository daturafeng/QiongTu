## Context

现有治理已经规定单一总控、任务边界、写入隔离、最多两个安全修复方向、可回退项目依赖优先安装和阻塞升级。此次只补充用户明确指定的模型路由，并必须服从 Codex 当前可用模型目录和运行时限制。

## Goals / Non-Goals

**Goals:**

- 让后续会话能从本地规则恢复“GPT-5.6 总控、GPT-5.5 执行窗口”的默认安排。
- 防止为了并行而并行，或在模型不可用时循环创建失败窗口。
- 保持总控对 OpenSpec、集成、验证和最终状态的唯一责任。

**Non-Goals:**

- 不保证任何外部模型在所有 Codex 版本、账号或时刻都可用。
- 不允许模型偏好覆盖安全、数据保护、OpenSpec、工具权限或运行时指令。
- 不改变既有阻塞重试和依赖安装边界。

## Decisions

### 1. 模型路由是默认执行配置，不是产品架构

总控窗口默认使用 GPT-5.6；由总控创建的新执行窗口默认使用 GPT-5.5。模型只影响开发任务路由，不成为穹图安装包、运行时或验收结论的一部分。所有窗口继续遵循同一 OpenSpec 和质量门禁。

### 2. 只有独立且值得并行的任务才创建执行窗口

总控先判断任务是否具有不重叠写入路径、明确输入输出和独立验收。没有实际并行收益、依赖同一未决决策或会修改重叠文件的任务保持总控串行执行，避免窗口数量本身成为进度假象。

### 3. 模型不可用时停止覆盖，不静默降级

若指定模型不在当前目录、模型目录在 Codex 启动后改变、当前运行时明确禁止覆盖，或创建窗口失败，总控不得静默改用其他模型或无变化重试。当前工作可在总控窗口安全串行推进；确需指定模型的并行任务保持待分配，并记录“重启 Codex”或其他用户可解除条件。

## Risks / Trade-offs

- [GPT-5.5 暂时不可用导致并行度下降] → 总控继续串行推进关键路径，不牺牲模型约束或反复创建失败窗口。
- [模型名称随产品目录变化] → 把可用性和运行时指令作为硬前置，不把模型别名当作永久 API。
- [过度拆分增加集成成本] → 仅为可独立验收且并行收益明确的任务创建窗口。

## Rollback

删除本变更新增的模型默认条款，恢复为“仅按用户当次指定且环境可用”的通用规则；不涉及产品代码或数据迁移。
