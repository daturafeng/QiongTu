## Context

开发治理主规格已定义 OpenSpec、任务就绪条件和风险门禁，但未明确代理何时应当对用户提出反对意见，何时必须先取得对重大替代方案的选择。本变更仅补齐该协作决策边界；动机见 `proposal.md`，可观察行为见本变更的 `development-governance` 增量规格。

## Goals / Non-Goals

**Goals:**

- 让技术反对意见可被理解、核验和选择，而非以无理由服从或泛化阻塞代替判断。
- 将用户确认限制在真正改变范围或外部影响的决策，维持已授权常规工作的推进速度。
- 使入口规则与治理主规格一致，供后续会话可靠恢复。

**Non-Goals:**

- 不赋予代理忽略用户明确目标或自行扩大项目范围的权力。
- 不要求对每个低风险、可逆的实现步骤重复确认。
- 不改变更高优先级的安全、合规、数据保护或系统约束。

## Decisions

### 1. 以“实质影响”而非主观偏好作为先询问门槛

只有替代方案显著改变成本、风险、架构、数据范围、外部影响或长期维护责任时，才要求先呈现选项并请求用户选择。代理必须给出与当前目标相关的事实和具体取舍；仅因存在不同实现偏好不得阻塞。

替代方案是“所有行动都先征求确认”。该方案会把常规执行退化为频繁问答，且削弱已明确授权的效果，因此拒绝。

### 2. 把硬性约束与技术推荐分开处理

安全、合规、数据保护和明确的 OpenSpec 目标冲突属于硬性约束：代理必须反对且不得直接执行。技术推荐属于可选择的方案：代理先呈现证据与取舍，等待用户决定。该区分避免把一般建议伪装成不可协商限制，也避免把硬约束当作可选偏好。

### 3. 在入口规则和主规格同时落地

`AGENTS.md` 提供每次会话都会读取的简明操作规则；`development-governance` 主规格提供可验证的完整契约。两者以相同的门槛和优先级表述，防止后续会话只读取入口规则时丢失要求。

## Risks / Trade-offs

- [“明显更好”被过度主观化] → 要求提供与用户目标相关的具体证据和实质影响，不以个人偏好阻塞。
- [确认过多拖慢工作] → 对已授权、低风险且范围不变的常规步骤明确要求直接执行。
- [用户坚持不安全操作] → 硬性约束继续优先，并提供安全替代方案。
- [入口规则和主规格漂移] → 提交前执行文本一致性检查与 OpenSpec 严格校验。

## Migration Plan

1. 添加本变更的治理增量规格、设计和任务。
2. 按增量规格更新 `AGENTS.md` 与主规格。
3. 运行严格校验和一致性检查；若失败，回退本次规则修改即可，不涉及用户数据或运行时迁移。
