# development-governance Specification

## Purpose

建立可由当前与后续 Codex 会话一致执行的软件开发治理契约，以 OpenSpec 为唯一事实来源，控制从目标验证、MVP、规格和设计到实现、测试、试运行、正式发布与持续迭代的完整生命周期。

## Requirements

### Requirement: 后续会话必须执行项目启动检查
任何涉及软件设计、实现、诊断、测试、发布或流程变更的会话 MUST 在采取行动前读取项目级 `AGENTS.md`、`openspec/config.yaml`、OpenSpec 当前状态以及适用变更的现有工件。会话 SHALL 继续已有变更，不得为同一目标建立平行的规划或事实来源。

#### Scenario: 新会话开始软件工作
- **WHEN** 新的 Codex 会话收到本项目的软件工作请求
- **THEN** 会话先确认 OpenSpec 可用、列出活动变更并读取适用工件，然后才进行设计或实现

#### Scenario: 找到已有适用变更
- **WHEN** 活动变更已经覆盖用户请求
- **THEN** 会话按现有 proposal、specs、design 和 tasks 继续，并在需要改变需求时先更新这些工件

### Requirement: OpenSpec 是唯一事实来源
项目 SHALL 使用 OpenSpec 保存需求、验收场景、技术决策、实施任务、任务状态和变更历史。项目 MUST NOT 使用 OpenSpec 之外的提案、设计或实施计划作为平行流程；其他说明文件只能引用 OpenSpec 或记录不与其竞争的操作性信息。

#### Scenario: 需求或技术决策发生变化
- **WHEN** 用户改变产品范围、外部行为、架构决策或兼容性要求
- **THEN** 会话在修改代码前更新所有受影响的 OpenSpec 工件并通过一致性校验

#### Scenario: OpenSpec 尚未初始化或不可用
- **WHEN** 仓库未初始化 OpenSpec，或当前阶段所需命令与工件不可用
- **THEN** 会话明确报告前置条件，完成安全初始化或请求用户处理，并在恢复前不开展软件设计或实现

### Requirement: 会话必须以证据审查用户指令并在重大分歧前取得选择
当用户请求与安全、合规、数据保护、已确认产品目标或已有 OpenSpec 决策冲突，或者代理基于具体证据判断存在明显更合适但会实质改变成本、风险、架构、数据范围、外部影响或长期维护责任的路径时，代理 MUST 说明冲突或取舍、证据、推荐方案和不推荐直接执行的原因。对于后者，代理 MUST 在执行实质性变更前请求用户明确选择；不得以无依据的反对、泛泛的风险提示或不必要的澄清阻塞已授权的常规步骤。安全、合规和数据保护要求优先于用户指令。

#### Scenario: 用户请求与已确认产品目标冲突
- **WHEN** 用户要求将某个开发期运行时设为最终独立桌面软件的强制安装依赖，但现有 OpenSpec 已确认最终产品不得依赖该运行时
- **THEN** 代理说明冲突、给出保持独立安装包的推荐路径，并在修改产品依赖前取得用户的明确选择

#### Scenario: 推荐路径会实质扩大影响
- **WHEN** 用户的目标可通过当前路径完成，但替代方案会新增外部服务、下载大量数据、引入许可义务或改变架构边界
- **THEN** 代理在采取该替代方案前说明各路径的主要取舍并请求用户选择

#### Scenario: 已授权的常规实现步骤
- **WHEN** 用户已明确要求执行某个任务，且下一步骤不改变已确认范围、不产生显著外部影响并符合安全与数据保护规则
- **THEN** 代理直接执行该步骤而不要求多余确认

#### Scenario: 安全或合规约束不能被覆盖
- **WHEN** 用户要求执行会违反安全、合规或数据保护硬性约束的操作
- **THEN** 代理拒绝该操作，解释适用约束，并提供可行的安全替代方案

### Requirement: 软件工作必须通过生命周期阶段门禁
项目 SHALL 按目标与成功指标、需求验证、MVP 定义、可验收规格、技术设计、任务拆解、实现、系统验证、发布准备、试运行、正式发布和运营迭代推进。除非用户明确缩小工作范围，后续阶段 MUST NOT 在其依赖门禁未满足时被宣称完成。

#### Scenario: 从想法进入产品定义
- **WHEN** 用户只有产品想法但目标用户、问题、价值或成功指标尚不明确
- **THEN** 会话先完成探索与假设记录，不直接选择完整技术栈或实现产品代码

#### Scenario: 从规格进入实现
- **WHEN** proposal、适用 specs、必要 design 或 tasks 中任一工件缺失或不一致
- **THEN** 实现保持未开始状态，直到所需工件完成并通过 OpenSpec 严格校验

### Requirement: MVP 必须形成最小完整业务闭环
每个首版或重要版本 SHALL 定义目标用户、核心问题、关键使用流程、范围内能力、明确非目标和可度量成功标准。MVP MUST 是可以完成核心价值验证的完整闭环，而不是缺少安全、错误处理、数据保护或发布能力的演示代码。

#### Scenario: 新增首版功能请求
- **WHEN** 一个功能不能直接支持当前核心用户流程或成功指标
- **THEN** 该功能默认移出 MVP，除非 OpenSpec 明确说明其阻塞完整闭环

### Requirement: 实现前必须满足 Definition of Ready
任务开始实现前 MUST 满足：关联的需求和验收场景明确、必要设计决策已解决、依赖和影响范围已识别、验证方法可执行、风险与回滚方式与任务风险相称。无法满足的任务 SHALL 保持待处理并记录阻塞原因。

#### Scenario: 任务验收标准含糊
- **WHEN** 开发任务无法从规格判断成功或失败
- **THEN** 会话先澄清或更新规格与任务，不以猜测开始编码

### Requirement: 实现必须以可验证小步推进并同步状态
实现 SHALL 按 OpenSpec `tasks.md` 的依赖顺序，以单次会话可完成和验证的小任务推进。每完成一项，必须在验证通过后同步对应复选框；失败、部分完成或未验证的任务 MUST NOT 标记完成。

#### Scenario: 完成一个实施任务
- **WHEN** 任务的代码、自动测试和适用手工验证全部通过
- **THEN** 会话将对应 OpenSpec 任务标记完成，并记录验证结果和剩余风险

#### Scenario: 发现规格外必要工作
- **WHEN** 实现过程中发现新增行为、重要架构变化或任务缺口
- **THEN** 会话先更新 OpenSpec 工件并保持一致，再继续实现

### Requirement: 完成项必须满足 Definition of Done
功能或变更只有在实现完成、代码经过自审或评审、自动测试通过、异常与边界场景处理、验收场景通过、必要安全与性能检查完成、文档和 OpenSpec 同步、并具备适用部署与回滚方式时 SHALL 被视为完成。

#### Scenario: 功能正常路径可用但异常测试失败
- **WHEN** 功能正常流程通过但适用异常、恢复或数据保护场景失败
- **THEN** 任务和变更保持未完成状态

### Requirement: 验证范围必须与风险相称
每个变更 SHALL 至少执行受影响范围的静态检查、单元测试、集成测试或端到端验收中的适用组合。涉及大文件、GPU、坐标、格式转换、安装升级、数据持久化、安全或发布的变更 MUST 增加相应性能、兼容、恢复或回滚验证。无法运行的验证 SHALL 明确记录原因、风险和替代证据。

#### Scenario: 修改成果格式或坐标转换
- **WHEN** 变更影响 GeoTIFF、点云、OBJ/FBX、3D Tiles、高斯格式或坐标变换
- **THEN** 验证包含外部工具或目标运行时回读、空间位置、轴向、尺度、格式完整性和兼容版本测试

### Requirement: 发布前必须通过发布门禁
正式版本 MUST 具备可重复构建、版本标识、测试报告、已知限制、兼容矩阵、安装/升级/卸载验证、数据备份与恢复说明、发布步骤和可执行回滚方案。高严重度缺陷、数据丢失风险、安全阻断或核心流程失败未解决时 MUST NOT 正式发布。

#### Scenario: 候选版本存在核心数据丢失缺陷
- **WHEN** 发布候选版本仍可能造成原始数据或正式成果不可恢复丢失
- **THEN** 发布被阻止，直到缺陷修复并通过恢复验证

#### Scenario: 首次面向真实用户发布
- **WHEN** 功能和系统验证完成
- **THEN** 项目先进行受控试运行并观察错误、性能、资源、处理成功率和用户反馈，再决定正式发布

### Requirement: 正式使用必须形成运营反馈闭环
正式发布后 SHALL 持续收集故障、性能、资源、成功率、用户反馈、安全更新和依赖变化。任何需要改变行为或设计的改进 SHALL 创建或更新 OpenSpec 变更，经过同样的规格、实现、验证和发布门禁。

#### Scenario: 生产使用发现新需求
- **WHEN** 试运行或正式使用数据表明需要新增或改变产品行为
- **THEN** 团队将其转化为新的或现有的 OpenSpec 变更，而不是直接修改生产实现

### Requirement: Git 可用后必须使用可追溯版本控制
仓库初始化 Git 后，源代码、OpenSpec、配置和必要迁移 SHALL 纳入版本控制。变更 SHALL 保持提交范围清晰、禁止提交密钥和大型派生成果，并在合并前通过适用检查；在 Git 初始化前，项目 MUST 明确报告缺少版本历史的风险，不得假装提交或分支门禁已经生效。

#### Scenario: 当前目录尚未初始化 Git
- **WHEN** 会话执行工程启动检查并确认不存在 Git 仓库
- **THEN** 会话报告该限制，继续仅执行不依赖 Git 的安全工作，并在需要版本控制操作前请求用户初始化或授权

### Requirement: 会话结束必须提供可继续的交接状态
完成软件工作后，会话 SHALL 报告活动变更、已完成任务、实际验证、未完成任务、已知风险和下一安全步骤。后续会话 SHALL 能仅依靠本地 `AGENTS.md`、OpenSpec 状态和工件恢复工作上下文。

#### Scenario: 会话在部分实现后结束
- **WHEN** 当前会话没有完成整个变更
- **THEN** OpenSpec 任务状态准确反映已验证进度，最终交接明确下一未完成任务和阻塞条件
